# Project Structure

Placement guidance for Extension Hub (Symfony 7.4 LTS / PHP 8.2+). All
commands run from the repo root.

## Where things live

- `src/Controller/` — thin HTTP controllers. Render the shell or return
  small responses; no business logic here.
- `src/Service/` — business logic, transformation, and export code (e.g.
  `ExtensionSnapshotBuilder`, `StaticSiteBuilder`, the `EgoSource*`
  classes). Put new logic here, not in controllers or entities.
- `src/Service/GitHub/` — the self-contained GitHub source subsystem
  (`App\Service\GitHub`): discovery, API client and cache, eligibility,
  image/metadata validation, source persistence, plus its result and
  value types. Class names carry **no** `GitHub` prefix — the namespace
  says it (`App\Service\GitHub\ApiClient`, not `GitHubApiClient`). This
  package references nothing else in `src/Service/`; keep that boundary.
- `src/Repository/` — Doctrine repositories using query builders.
- `src/Entity/` — Doctrine entities (public typed properties are
  intentional).
- `src/Dto/` — snapshot/score DTOs (e.g. `ExtensionSnapshotItem`,
  `ScoreComponents`).
- `src/Command/` — Symfony console commands (`app:update-extensions`,
  `app:parse-comments`, `app:build-extension-snapshot`,
  `app:build-static-site`).
- `templates/` — Twig templates. Shell/composition only; see
  `docs/agents/conventions.md`.
- `assets/app/` — hand-written browser modules (list/detail/filter UI,
  kebab-case filenames); this is where feature JS work happens.
- `assets/app.css`, `assets/app.js` — the only Vite entrypoints
  (Tailwind 4 + DaisyUI). Vite is the sole asset pipeline; there is no
  AssetMapper/importmap, no Stimulus and no Turbo in this project.
- `tests/Controller/`, `tests/Service/`, `tests/Service/GitHub/`,
  `tests/Command/`, `tests/Repository/` — PHPUnit, mirrors `src/` layout
  including the `GitHub` subnamespace.
- `config/` — Symfony bundle config and `services.yaml` (autowire,
  autoconfigure). Do not touch without understanding the bundle it
  configures.
- `migrations/` — Doctrine migrations.
- `docs/todos/` — local task tracking (see `docs/agents/commands.md`).
- `docs/prd/` — product requirements for planned work (e.g. GitHub
  extension indexing); read before implementing related features.
- `docs/superpowers/schema/` — the **public** extension feed contract
  (`extensions-feed.md` + `extensions-feed.schema.json`). Third parties
  and `ExtensionSnapshotBuilderTest` depend on it; treat it as an
  external API, not as internal notes.

## Generated vs. hand-edited — do not edit generated output directly

- `vendor/`, `node_modules/`, `var/` — generated/ignored. Regenerate via
  Composer/npm, never edit by hand.
- `public/data/` — generated JSON snapshots, ignored locally; regenerate
  via `app:build-extension-snapshot` / `app:parse-comments`.
- `public/build/` — generated by `npm run build`, **committed** to git.
  Edit `assets/`, then rebuild; never hand-edit files under
  `public/build/`.
- `dist/` — generated by `app:build-static-site`, **committed** to git,
  except `dist/data/*.json` (ignored; see below). Edit
  templates/assets/services, then rebuild; never hand-edit files under
  `dist/`.
- `dist/data/` — nightly extension/comment JSON snapshots, ignored
  locally and not committed; the Cloudflare Pages deploy workflow
  downloads current copies from the snapshot origin and writes them
  into `dist/data/` right before deploying (see
  `docs/cloudflare-pages.md`).

## Binding docs before you touch these areas

- UI markup, colors, layout → `DESIGN.md` is binding; read it first.
- Domain naming (entities, fields, terms) → `UBIQUITOUS_LANGUAGE.md` is
  binding; read it first.
